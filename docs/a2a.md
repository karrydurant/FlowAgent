# 第0讲----一次Agent协作里都有谁

### 先走一个简单例子，有一个故障诊断工作流跑到某个节点，要问另一个 Agent 一件事

第一步：开会话

工作流节点调网关注册一场会话。网关拿着名单逐个查注册中心：这个 Agent 在线吗? 它登记了投递地址吗？任何一个人查不到，整场会话直接拒绝，一个请求都不发。

第二步：会话和成员落盘

生成的会话对象里，除了名单，还额外记了每个人的投递地址快照和本次角色。地址为什么快照，等下讲。

第三步，投一条 REQUEST

投一条 REQUEST。 落进 Redis 的消息长这样：

| 字段 | 值 |
| ---- | ---- |
| messageId | 服务端生成的唯一标识，比如 m-8f21 |
| sessionId | 这场会话的 id |
| seq | 1--会话内序号，由 Redis 分配 |
| fromAgentId | repair-agent |
| toAgentId | log-agent |
| kind | REQUEST |
| payload | {task: "查一下昨晚 2 点的错误日志"} |
| replyTo | null 意味着这是新起的话头，不是回复 |
| importance | NORMAL |
| createdAt | 投递时刻 |

第四步，叫醒对方

消息落盘之后，再给对方的实例发一句 “你有新消息”。注意这里是两件事：写一次，叫一次。为什么不是顺手在"叫醒"里把消息也写一遍，这是第 2 讲的核心。

第五步，对方来读

log-agent 收到叫醒，带着自己的游标去读会话日志，要求“只给我序号大于 N 的”。它读到 seq=1 这条，真的跑一遍自己的 Agent 循环。

第六步，回报

log-agent 拿到答案，投一条 REPLY 回去，replyTo 填的是第一步那条的 messageId (m-8f21)。

第七步，配对

发起方一直在同一场会话里等，等的条件不是"来了一条消息"，而是"来了一条 replyTo 等于我那条 messageId 的 REPLY"。对上了，把答案拿走继续往下跑。

第八步，收尾

会话转成已关闭，日志留在那里。事后按会话 id 就能把整个过程读回来——这是唯一的事后复盘入口。

### 抽象成骨架

把上面 8 步里出现过的东西归类，分为 3 类

会话（这次协作的容器）

成员表（谁参加，怎么找他，他这次是什么角色，例如
| repair-agent | 快照地址 | 召集人）

消息日志（谁对谁说了什么，按会话内序号排，例如
| seq=1 | REQUEST | repair-->log |）

外加一个不在这三张表里、但贯穿始终的东西：Redis。会话、成员、日志都存在那儿，而且会话日志是唯一真相，收件箱之类的结构只存指针、不存副本，就是为了不出现第二个真相。

还有一句要记住的总纲，后面每一讲都在解释它：

委派、协商、主动通信这三种看起来不同的协作，在这个项目里是同一条通道的三种用法。

委派 = 发一条 REQUEST 等 REPLY；协商 = 多轮 PROPOSE 收敛；主动通信 = 发一条 INFORM 不等回复。区别只在"谁发起、等不等回复"。

好处不是省代码，是鉴权、防环、留痕各只有一份。这个项目在被改造之前，委派和协商各走各的路，结果是两条路各有一份超时、各有一份失败处理——第 5 讲会看到那份超时后来怎么变成事故。

### 三个结构

A2aMessage

| 字段 | 类型 | 含义 |
| ---- | ---- | ---- |
| messageId | String | 消息唯一标识，服务端生成 |
| sessionId | String | 所属会话 |
| seq | long | 会话内单调递增序号，存储层分配，用作增量拉取的游标 |
| fromAgentId | String | 发送方 |
| toAgentId | String | 接收方，null 表示广播 |
| kind | enum | 消息种类，同时是 payload 的结构选择器 |
| payload | Map | 消息体，结构由 kind 决定 |
| replyTo | String | 本条回复的是哪条消息（填对方的 messageId）|
| importance | enum | NORMAL/CRITICAL |
| createdAt | Instant | 投递时间 |

kind有六个值，各自的约定

| kind | 谁发 | payload | 会不会触发对方干活 |
| ---- | ---- | ---- | ---- |
| REQUEST | 委派方 | {task, depth?} | 会 |
| REPLY | 被委派方 | {success, answer} 或 {success:false, error}，必须带 replyTo| 不会 |
| SOLICIT | 协商召集人 | {decision, confidence, reason}，必须带 replyTo | 不会 |
| PROPOSE | 协商参与者 | {vote} | 不会 |
| INFORM | 任何成员 | 自由结构 | 不会 |

importance 这个字段容易被误读成"消息优先级"。它其实只服务一件事：Agent 的历史窗口在上下文变长时会收紧，收紧时默认只留最后 4 步，一次多 Agent 协作很容易超过 4 步，"先别动生产库"这类早期关键约束会被悄悄裁掉。所以消息可以自报关键，裁剪时关键消息不被丢——这是它存在的唯一理由。

A2aSession 

| 字段 | 类型 | 含义 |
| ---- | ---- | ---- | 
| sessionId | String | 会话唯一标识 |
| topic | String | 这次协作要解决的事；协商场景下就是议题 |
| initiator | String | 发起方 |
| members | List<Member> | 成员表，含发起方自己 |
| status | enum | OPEN/CLOSED/EXPIRED |
| messageCount | int | 已投递条数，用于消息预算判定 |
| fromRunId | String | 由哪次工作流运行发起；null=不是工作流发起的（用户在会话台当场开的） |
| fromNodeId | String | 由哪个节点发起；null 含义同上 |
| createdAt | Instant | 创建时间 |
| updatedAt | Instant | 最后一次状态变更时间 |

Member

| 字段 | 类型 | 含义 |
| ---- | ---- | ---- |
| agentId | String | 成员标识 |
| endpoint | String | 开会话时从注册表快照下来的投递地址 |
| role | enum | 本次协作里的角色 |
| joinedAt | Instant | 加入时间 |

role四个值

| role | 含义 |
| ---- | ---- |
| PARTICIPANT | 普通参与者，投一票，票数参与聚合 |
| VETO | 持否决权，投反对即终止讨论，不看票数 |
| SUPERVISOR | 主管，不投常规票，各方意见齐了之后被单独征询裁决 |
| CONVENER | 召集人，不表态，负责投出每一轮的议题 |

### 表后面的隐含规则

1.seq 只在会话内单调，跨会话不保证。 所以消费方永远带着会话 id 查、拿它当游标。任何"全局消息序号"的想法都是错的。

2.toAgentId 为 null 就是广播——投给除发送方以外的全部成员。这个语义靠"字段缺席"表达，所以这个类刻意不加"忽略空字段"的序列化设置。加了之后行为不变，但排查时会让人以为"广播"和"字段没写"是两回事。

3.replyTo 是配对键，不是装饰。委派的等待逻辑靠它配对。没有它，一场会话里并发起两次委派就会互相串台——B 的回复被 A 收走。

4.会话状态只有两条转移，没有"重开"。 只能 OPEN → CLOSED（正常收尾）或 OPEN → EXPIRED（过期）。往已收尾的会话里追加消息，会让"这次协作的结论是什么"永远答不出来——结论之后又来了两条，算不算数？要继续讨论就开新会话，用 topic 说明关系。

5.成员的地址是快照，不是引用。 因为注册表里的地址是可变的（Agent 重启后可能换端口）。如果会话中途去重读注册表，会出现"同一次协作里前两条消息打到 18080、后两条打到 18081"——接收方换了实例，它看不见前面的上下文。

6.角色是"本次协作的属性"，不是"Agent 的属性"。 同一个安全 Agent，在这次评审里是否决者，在另一次里只是普通参与者。所以角色由本次发起方指定，不从注册表推导。

另外还有一条关于 CONVENER 的，比较绕，先记着：它存在是因为总得有人在问。会话里任何一条消息都要有发送方，而发送方必须是成员；召集人若同时也是参与者，它就投不出"征询自己"这条消息（自己发给自己会被防环闸拦下），结果是名单里第一个人永远不表态。

### 如果删掉"会话"这一层，让 A 直接调 B 的接口，会丢什么？(为什么不让 A 直接调 B 的接口，而是要开一个会话)

先看 "直接调"：

A -> POST/workflows/execute (B 的定义+任务) 阻塞等 HTTP 响应 <- B 返回结果

丢失了什么：

1.没有共同的过程记录：

这次协作留下的痕迹是两份互不相干的东西：A 的运行记录在 A 那边，B 的运行记录在 B 那边。想问"这次到底怎么谈的、B 有没有改过口"，只能拿时间戳去两边对。

2.只有 "一问一答" 这一种形状：

请求-响应天生只表达一种关系。但实际有三种：
  
- 协商要多轮，而且第 2 轮必须带着第 1 轮各方的意见。直接调要么把上下文一路手动往下传（越传越大），要么每轮重新描述一遍。

- 主动告知（"告诉 B 一件事，但不要它回复"）没有对应形状，只能硬塞一个假响应。


# 第二讲----谁能被找

上一讲讲的是 "一条消息怎么走完全程"，但有一个问题：发起方是怎么知道可以找谁的

### 先走一个具体例子

场景：repair-agent 正在跑它的 ReAct 循环，它需要问 log-agent 一件事。

第一步：每轮推理前先问"我有哪些工具"。

循环每走一轮，构建提示词之前都会去问一遍工具表。这里拿到的不是某个具体的桥，而是合成的那个 -- 它内部做两件事：问 MCP 工具表，问同伴表，然后并成一张

第二步：同伴表是怎么算出来的

它去调网关的一个查询接口，背后是注册中心的一个方法，这个名字很关键：列"可用的"。这个方法同时滤掉两样东西——心跳过期的，以及声明了不接受委派的。所以"在线"和"可以被委派"是两件事，一个人可能在线但不接受派活。

每个回来的 Agent 变成一行工具描述。描述它卡片上的说明文字，取不到就依次退到 "专长"、"名字"，最后退到它的 id 本身。这个兜底链是为了不渲染出一行 - log-agent: null 这种模型没法用来选人的东西。

第三步：并集之后按白名单过滤
合成的工具表是 "工具在前、同伴在后"，然后用这个 Agent 自己的白名单过一遍。白名单里写了 log-agent，它就留下。于是提示词里多出这一行：

log-agent: 负责排查线上服务的日志

第四步：模型选人

模型看到这一行，输出 Action:log-agent。此时模型做的事和它选工具是同一个动作，它不知道自己在 "委派"，它只是在挑一个工具用

第五步：调用时分岔

这个动作回到合成桥，它按 "最近一次列举出来的同伴名字" 判断：log-agent 在同伴集合里 -> 转给同伴桥，去开会话，投消息，等回复。不在集合里 -> 交给 MCP 工具那边

### 抽象：四层各管什么

|层|回答的问题|
| ---- | ---- |
| 注册中心 | 有哪些 Agent 在线、接受委派、地址在哪 |
| 同伴桥 | 把每个在线的同伴变成一个"工具" |
| 合成桥 | 工具表和同伴表合成一张，并记住哪些名字是同伴 |
| 白名单 | 这个 Agent 到底能看见谁 |

### 三处值得单独记的设计

1.列举失败降级为空表，不是让节点失败。

网关抖一下，不应该让每一个 Agent 节点都跟着失败。降级成"当前没有同伴可委派"，Agent 照常跑完，只是这次不找外援。这条路径是这套东西能起来的前提。

2.名字冲突时以"工具"为准，而且路由必须跟显示一致。

如果某个 MCP 工具的名字恰好等于某个 Agent 的 id，保留工具、丢掉同伴，并告警一次（同一个名字只报一次——这个列举每轮都跑，每次报就是刷屏）。

关键在于必须一致：表里显示的是工具，调用时就必须走工具那条路。如果显示工具、路由到同伴，那用户看到的和实际跑的不是同一个东西

# 第三讲----执行

第二讲停在 "对方被叫醒了"。这一讲跟完剩下的路：被叫醒的实例怎么把活干完，再把结果投回去。

### 一个入口，两条来路

PeerDispatcher.dispatch 它的签名只有两个参数：

```java
public void dispatch(String sessionId, String messageId)
```

没有消息本身。这是第 2 讲那个设计的直接后果 —— 唤醒的 body 里就只有 sessionId，messageId，seq，fromAgentId，kind，没有 payload。所以执行者拿到的只是一句 "这条消息归你了"，正文要自己去 Redis 里读。这个 "通知不带正文" 的选择，在这里兑现成 "只有一份真相"

两条来路：本实例的成员由 SessionManager.deliver 直接调，跨进程的由对端的 /sessions/{id}/wake 端点转调。两条路汇到同一个方法，所以本地委派和跨进程委派在行为上没有分叉。

### 第一步：幂等闸，在调用方线程上同步做

```java
if (!markHandled(messageId)) {
  log.info("[A2A] 这条消息已接手过，跳过重复派发 ...");
  return;
}
```

必须在提交之前、且在调用方的线程上同步做
