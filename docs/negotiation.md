# 协商

## 协商的几种方式

| 模式 |  | 怎么出结论 | 没有结论时报什么 |
| ---- | ---- | ---- | ---- |
| voting | 多数票 | 数票，置信度不参与 | 平票 no_majority；全员弃权 undecided |
| consensus | 必须全体一致 | 无弃权 + 立场唯一 | no_consensus（附 uniquePositions）|
| weighted | 加权投票 | 分数 = 权重 × 置信度 | 平票 no_majority；全零 undecided |
| supervisor | 主管裁决 | 先收各人意见，再交给一个主管 Agent 写裁决 | undecided（附 supervisorError）|

voting：弃权不算一票但算分母的意思就是总票数不能因为它弃权就-1

主管不必事先列进参与协商的Agent（前端可以看到勾选参与协商的Agent），代码会自动把它加进成员表

另外还有两个开关：vetoAgentIds（指定谁有一票否决权。这些人投 reject 就当场终止讨论，结果变成 decision = "reject"，并带上 vetoedBy。这一条对四种模式都生效，是叠加在模式之上的。）

## 协商要把同一个问题一次发给好几个 Agent。为此专门写了一套发送的办法吗？还是借用了本来就已经有的那套（开会话 → 往里写一条消息 → 叫醒对方）？

没有另写。 协商里"把问题发给某个 Agent"用的就是委派里同一个动作--sessionManager.post(sessionId, ...)

这件事的价值在于：如果是协商自己写一套发送，就得自己解决"对方不在本进程怎么办"

## 协商第二轮比第一轮多了什么，为什么只有第一轮就不算协商？

先假设一个场景：这场协商有三个人要表态：诊断 Agent、修复 Agent、安全 Agent。召集人（就是协调这次协商的那一方，a2a-convener）负责问。

第一轮做两件事：

1.把问话发出去，并记录：

召集人往会话里写三条消息，分别给三个人。每条消息系统会分配一个编号(messageId)。写完这三条之后，召集人手里多了一份 "统计"：

a2a-msg-111  →  诊断 Agent

a2a-msg-222  →  修复 Agent

a2a-msg-333  →  安全 Agent

一会儿回答回来的时候，是三条平铺在会话日志里的消息，召集人得能认出哪条是谁的（每条回复里有一个字段 replyTo，写着"我是在回哪一条问话"。比如"修复 Agent"回的那条，它的 replyTo 就是 a2a-msg-222。拿 222 去查纸条 → 这条意见是修复 Agent 的）。

2.等这三条回复回来。

收齐（三条都到）或者时间到（撞上 deadline），就停。不会一直等下去。

3.补齐

照着"我本来要问谁"的名单过一遍。每个人：有真实意见就用真的；没有就补一条弃权，并且把这个人的名字写在弃权上。

第二轮存在的理由：

因为第一轮的问话里不带上一轮的意见，三人是各答各的，不知道别人说了什么

第二轮的问话里塞进了第一轮各方的意见摘要（代码里叫 prior），这段摘要会被渲染进提示词。所以第二轮里，修复Agent 能看到 诊断Agent 和 安全Agent 第一轮是怎么说的，从而改口。

只问一轮就数票，那是"同时问了三个人的看法"；看得见别人说了什么、可以因此改口，才是协商。 

## 协商不会一直谈下去，是什么让它停下来？

|  | 管什么 | 为什么必须有它 |
| ---- | ---- | ---- |
| maxRounds(默认 3)| 谈几轮 | "各方永不改口"是完全正常的局面——没有轮次上限且时间还没到，就会一轮一轮问下去，每一轮都在烧 LLM 调用 |
|deadline（min(调用方预算， 60s)）| 总共谈多久 | 一个 deadline 管全程，不是"每个成员各 30 秒"；否则 N 个成员 M 轮就是 N×M 个独立窗口，总时长没有上界 |
| unanimous(opinions) | 还用不用谈 | 已经一致就没必要再问一轮 |

maxRounds 到了但还没一致 → 带着分歧出结论；deadline 到了但才第二轮 → 同上；一致了但还有轮次余额 → 提前停。收尾是带着已有意见出结论，不是丢弃——"谈了三轮只剩最后一票没回来，仍然是一份能用的结果"。

deadline 还有个只能压短的规矩：min(调用方预算， 60s)，压短时记一条 WARN。

## 一场协商里，谁有资格表态？

votersOf：成员表里角色是 PARTICIPANT 或 VETO 的席位。召集人和主管不在其中——他们不表态。

## 有人弃权，这一票算不算

虽然不算一票，但是也不是完全当作没有

## 赞成和反对的票数一样多，最后报什么

报 no_majority，不给结论。winnerOf 取最高票，如果取到最高票有两个，就返回 no_majority。因为出现平票是很常见的，不能随便选一个。

## 参与方回答时要自己报一个 0~1 的把握分。如果所有参与方都没报这个数，加权投票算出的是什么结论？

参与方回答问题时不是自由发挥，要交一段 JSON，长这样：

{"decision":"approve", "confidence": 0.9, "reason": "降级预案已经验证过"}

decision：立场，只认 approve / reject / abstain 三个词

confidence：0 到 1 之间的一个数，由参与方自己填——"我投赞成，我的把握是 0.9"。它不是系统算出来的，是模型自己报的

reason：一句话理由

加权投票算分的方式：权重*置信度

权重由发起方在 context.weights 里给，比如"安全 Agent 的话权重 3"。没给的默认 1.0

置信度就是上面那个参与方自报的数，没填默认 0。全都是 0 相当于没有任何有效信息，报 undecided

## 参与方回了一段自然语言，不是约定的 JSON，这一票怎么处理？

记弃权，不做关键词兜底。在 parse 解析模型返回时只做一件事容错：模型常把 JSON 包在解释性文字或代码围栏里，所以先整体试解析，失败再从第一个 { 到最后一个 } 截一段试。
截不出来就是弃权，然后 reason 里放原始回答（截断到 200 字符）。
