# Agent 之间是靠什么通信的？点对点调用、消息总线、还是共享状态？为什么这么选？

是混合的，有分工：内容是共享状态，通知是点对点。

一次投递（SessionManager.post）做两件事：

1.把消息落盘进 Redis 里的会话日志 —— 这是共享状态。

2.叫醒收件人 —— 这是点对点 HTTP。

第 2 步只送一个指针（"去会话里读第 5 条"），不送内容。所以：

内容永远只有一份，在共享状态里；通道上跑的是"有新消息"这四个字。

为什么不用纯点对点：

没有留痕（事后查不到这次协作发生过什么）；超时和失败处理要给每个调用方各写一份；防环要另做一套；两个人同时问第三个 Agent 会串台。改成会话之后，这些全部由会话这一层统一解决。

为什么不用消息总线：

一条消息进了队列，被消费掉就没了；而这个项目要的是能按顺序整段读回来复盘。它没有总线带来的解耦和削峰。生产者要等消费者的唤醒请求返回，也没有排队缓冲突发。换来的只有一件事——事后可查

三种消息 INFORM / PROPOSE / VOTE 没有任何人在等回复，它们走不了"投递—等回"那条路。所以另有一条补的通道：收件箱。A2aInboxClient.drain() 在每轮推理前拉一次，"我有没有新消息"由网关回答。

这是整条通信线上唯一非请求-响应的部分，也正是它让"共享状态"这一侧真正被用起来了——否则会话日志就只是个被动的记录本。

一个实现取舍：A2aInboxClient 走 HTTP，不直接读 Redis。原因是会话存储在 flowagent-a2a-gateway 模块里，而引擎模块的 pom 不依赖它。加一条依赖边会把引擎和 A2A 的存储实现绑死。
本机部署时这次调用是发给自己，代价是一次 loopback HTTP。

## 哪些数据是所有 Agent 都能看到的，哪些只有一个 Agent 自己看

|  | 会话日志 | 记忆 |
| ---- | ---- | ---- |
| 作用域 | sessionId | (sessionId, agentId) |
| 谁能看 | 全部成员 | 只有那一个Agent |
| Redis key | fa:a2a:session:* | fa:session:mem:{sessionId}:{agentId} |
| 内容形态 | 结构化消息（kind + payload，有 seq 顺序）|  |
