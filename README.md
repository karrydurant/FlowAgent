# FlowAgent
一个多 Agent 工作流编排系统。
假设有十几个各管一摊的 AI，怎么让它们像一条流水线那样配合干活，并且整个过程还在掌控范围内-----这个项目的目的就是初步实现这些功能。

## 执行引擎部分
#### 执行引擎的功能
你脑海中有了各个 Agent 工作的顺序：谁在谁之前工作，谁和谁一起干，谁的工作结果又是怎么决定后续流程走向的。执行引擎就是把你的想法实现。另外它还会处理中间有个Agent节点失败了怎么办，卡住了一直不出结果怎么办，~~进程崩了从哪里接，要等人签字的怎么不占线程，两个副本抢起来谁说了算~~，目的是让这个工作流无论遇到什么都会被忠实地跑完，或者明确地停下来。
#### 在实现功能之前
需要先保证一件事：整个工作流是一个单一入口的有向无环图。代码中通过 kahn 算法对其进行判断和分层，如果发现你构建的工作流处理不了的话会~~干什么~~。
#### 三种线程池
对应两种执行粒度和一个中间角色：
工作流池承载一个工作流，节点池承载一个节点；中间角色负责的仍是节点 -- 每个节点配一个监工线程，它不执行任何业务逻辑，只负责拿到并发许可、提交节点任务、监测超时
**为什么要有中间这一层**
给监工单独分出一个池而不是让工作流线程自己等：如果工作流线程 "先等节点 1，等完了再等节点 2"，那就失去了同一层的并行，如果 "一次性把 10 个干活任务全提交上去，然后等‘全都完成’"，那就丢掉了每个节点独立的超时，只剩下一个整体超时了。一个监工盯一个节点，才能做到 "每个节点有自己的超时限制，超时了单独处理，其它接着跑"
##### 三种任务需要什么参数，返回什么结果，具体的执行逻辑是什么
**工作流任务**
接收 WorkflowDefinition，WorkflowRun
内部执行顺序是：
1.抢执行租约（Redis 上的一把锁），抢不到就落 FAILED 返回
2.抢到了就落状态 RUNNING，记开始时间，写一条 WORKFLOW_START
3.登记到 fa:workflow:inflight 索引（给兜底扫描用）
4.建 Deadline（全局超时的截止时刻）
5.开一个链路追踪的 span
6.TopologicalSorter.sort(definition) —— 把整张图切成层
7.循环每一层：
filterByConditions —— 这一层里哪些节点该上（条件分支的判定在这）
一个都不该上 → 直接下一层
executeLayer —— 把该上的节点跑完
跑完看状态，不是 RUNNING 就 break
8.再补判一次全局超时（防最后一层的超时被漏判）
9.状态还是 RUNNING → 落 COMPLETED，写时间线，删掉 Redis 快照
10.出异常 → 先顺着 cause 链找挂起信号，有就走挂起流程，没有就落 FAILED
11. finally：放租约 → 移出运行中集合 → 是终态就从索引摘掉 → 存进最近结束的缓存 → 关 span
最后什么都不返回，结果全部体现在 run 这个对象上：run.getStatus() 是 COMPLETED 还是 FAILED 还是WAITING_APPROVAL，run.getTimeline() 里发生了什么事。

##### 分出三个池的目的：
假设只有一个池，10 个线程。现在有一层 10 个节点要跑：
1.工作流线程把 10 个"监工"任务提交进这个池 → 10 个线程全被监工占了
2. 每个监工要提交一个"干活"任务进去 → 池里没线程了，干活任务只能排队
3. 监工在等干活任务的结果，干活任务在等一个空闲线程（但是不会有空闲线程了）
4. 出现资源死锁
另外也可以根据三种任务的不同特性，为线程池定制配置。
工作流池：一个工作流占一个线程好几分钟，线程池开小一点（core 2/ max 8），使用的是有界队列（256个）
监工池：全是纯等待，几乎不占用 CPU，按需扩容
节点池：消耗 CPU 和网络，也按需扩容
